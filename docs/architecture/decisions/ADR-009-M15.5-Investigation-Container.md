# ADR-009 Amendment: M15.5 Investigation Container (Story 1)

- **Status:** Accepted (amendment to ADR-009)
- **Date:** 04-08-2026
- **Parent ADR:** [ADR-009 Web Platform REST](ADR-009-Web-Platform-REST.md)
- **Release:** `v2.3.0` — Story 1: Create an Investigation
- **Prior amendment:** [ADR-009-M15.3 Shared Investigations](ADR-009-M15.3-Shared-Investigations.md) (`v2.2.0`)

---

## Context

`v2.2.0` introduced **shared workspaces**: server-persisted named containers with one log snapshot and session state (`WorkspaceStore`, `/api/v1/workspaces`). That solved save/list/reopen for a **single log** but not a production incident workflow where engineers collect **multiple files** (logs, notes, and later cores, traces).

Product language shifts from **workspace** (implementation) to **investigation** (user-facing noun). The persistence directory and `web.workspace_dir` key remain; the domain model is new.

Constraints unchanged from ADR-009: C12 thin handlers over **ApplicationService**; offline single process; file-first persistence; CLI parity for analyze/investigate after open.

---

## Decision

### 1. Investigation is the domain concept

An **Investigation** is a portable incident container identified by **UUID**. It groups **artifacts** (files and notes) and optional session snapshot state. Users create, add to, save, and reopen investigations — not "workspaces."

**Workspace** remains **storage and API compatibility** only (`web.workspace_dir`, legacy `/api/v1/workspaces` routes). It is not the product noun.

### 2. Investigation is the aggregate root

All mutations go through the **Investigation** aggregate:

- Add / remove artifacts
- Set entry artifact (`primaryArtifactId`)
- Save / load session snapshot
- Update name, description, tags

External code must not write artifact files or manifest fields outside the aggregate API. This keeps a single consistency boundary as Story 2–4 add artifact types without scattering logic across parsers or presentation layers.

### 3. Artifacts are entities

Each artifact has a stable **UUID** within the investigation, a **type** string (`log`, `note` in `v2.3.0`), metadata, and on-disk payload. Artifacts are **entities** (identity matters), not value objects.

**Entry artifact:** `primaryArtifactId` designates which artifact opens into the active analyze/investigate session. In `v2.3.0`, open requires entry type `log`; other types return `409` until crash/core handlers exist in a later release.

### 4. Type handlers (extensibility without plugin framework)

Artifact `type` maps to **`IArtifactHandler`** implementations:

| Type (`v2.3.0`) | Handler role |
|-----------------|--------------|
| `log` | Store file bytes; resolve path for `ApplicationService::openSource` |
| `note` | Store UTF-8 text; no analyze in `v2.3.0` |

New types (e.g. `core`, `pstack`) register additional handlers in later releases **without** changing the Investigation aggregate shape or manifest major version.

The Investigation aggregate does **not** import analysis, investigation engine, reporting, AI, or timeline modules. Handlers perform storage validation; presentation layer calls **ApplicationService** after resolving paths.

### 5. On-disk layout (manifest schema v1)

```text
{web.workspace_dir}/{investigationId}/
  manifest.json
  snapshot.session          # optional — existing session format
  artifacts/
    {artifactId}/
      meta.json
      data
```

**`manifest.json`** (schemaVersion `1`): `id`, `name`, `description`, `createdAt`, `updatedAt`, `primaryArtifactId`, `tags`, `metadata`, `artifacts[]` (each with `id`, `type`, `name`, `relativePath`, `importedAt`, `source`, `status`, `tags`, `metadata`).

**Migration:** Directories created by `v2.2.0` `WorkspaceStore` (legacy `metadata.json` + `snapshot.session`) are read as investigations with one synthesized `log` artifact. No automatic rewrite on read; rewrite on next save.

### 6. REST API

New primary routes under `/api/v1/investigations`:

| Method | Path | Purpose |
|--------|------|---------|
| `POST` | `/api/v1/investigations` | Create |
| `GET` | `/api/v1/investigations` | List (bounded) |
| `GET` | `/api/v1/investigations/{id}` | Metadata + artifact index |
| `PUT` | `/api/v1/investigations/{id}` | Update metadata / entry artifact |
| `DELETE` | `/api/v1/investigations/{id}` | Remove tree |
| `POST` | `/api/v1/investigations/{id}/artifacts` | Add log or note |
| `GET` | `/api/v1/investigations/{id}/artifacts/{artifactId}` | Artifact metadata / body |
| `DELETE` | `/api/v1/investigations/{id}/artifacts/{artifactId}` | Remove artifact |
| `POST` | `/api/v1/investigations/{id}/open` | Load entry artifact into `X-LogScope-Session` |

**Workspace alias:** Existing `/api/v1/workspaces/*` handlers delegate to the same store (same UUIDs). Deprecated in documentation; removal not before `v2.4.0`.

**Session save:** `POST /api/v1/sessions/save` accepts `investigationId` (preferred) or legacy `workspaceId`.

Session header, API key middleware, and error envelope unchanged from ADR-009 §4.

### 7. CLI

New command group `logscope investigation` — `create`, `add`, `add-note`, `list`, `show`, `open` — operating on investigation directories. Existing `session` commands unchanged.

### 8. Core module location

Investigation aggregate and handlers live in **`core/workspace`** (`scope_workspace`), extending the module that already owns `InvestigationSession` and `SessionSerializer`. No new top-level `core/investigation` library in `v2.3.0`.

## Consequences

### Positive

- One domain model supports Stories 1–4 without redesign.
- Workspace users and API clients keep working via alias and migration read path.
- Clear boundary: Investigation owns artifacts; ApplicationService owns analyze/investigate.

### Negative / risks

- `WorkspaceStore` refactor must preserve `v2.2.0` integration tests until migration coverage lands.
- Entry artifact must be `log` in `v2.3.0` — document clearly for API consumers.
